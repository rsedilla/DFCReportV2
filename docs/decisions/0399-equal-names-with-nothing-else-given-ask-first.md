# 2026-10-28 — Equal names with nothing else given ask first

Owner ruling, 2026-10-27, chosen from screenshots of Add People today beside the screen that asks
(option B), from the duplicate audit of 25 Oct.

## The ruling

**1. An exact first and last name match stops and asks, where neither a birthday nor a mobile
number is given.** When a person is added with both marked *Not given yet* (decision 0328), and
somebody already recorded has the same first and last name, Add stops at "Is this someone already
recorded?" as it does for a strong match (Tier 1), with the reason "first and last names equal, and
no birthday or mobile number to tell them apart". "These are different people — add anyway" adds
them. Until now the names were shown as a possible match (Tier 2) and Add went through, so the one
case with nothing to tell two records apart was the one case nothing asked about.

**2. It reads what was given, never what the other record holds.** Whether the existing person
has a birthday or a mobile number recorded makes no difference, so the stop says nothing about
either (Section 8). Names "equal" means equal as Section 3 compares them: a nickname or a one-letter
difference is not reached by this rule.

**3. Edit details asks the same**, because decision 0396 checks an edit as creation is: an edit
that leaves a person with neither a birthday nor a mobile number, and changes a name so that it
equals somebody else's, stops and asks. The pre-flight list shows the same reason before Add is
pressed.

**4. What is unchanged.** A namesake the encoder may not see does not stop the save, as no Tier 1
candidate outside their branch does: they cannot be shown in full. The tree import is unchanged:
its rows carry no *Not given yet* tick, and its decisions file is settled.

Section 3 said absence was honest and that "less is known, so less is claimed". That stays true of
a match that rests on a birthday; this ruling asks first where the names are all there is.
